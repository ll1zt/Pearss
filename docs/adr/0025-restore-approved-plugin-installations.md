# 0025 · 从持久化审批记录恢复插件安装

- 状态：accepted
- 日期：2026-09-17
- 部分 supersedes：ADR 0023 的安装来源判定与「无源插件永不执行」描述；其余信任、卸载和隔离决策保持不变。

## 背景

ADR 0023 要求安装记录参与启动装载，但实现仅在进程内保存已安装注册项。
新进程能读到数据库行，却无法用该插件采集。另一个实际差异是随服务发布的
沙箱采集器也使用 `trust="third-party"`；不能把这个字段当成安装来源。

## 决策

启动时，先读取当前 tenant 的 plugin 表，排除 `_DECLARATIONS` 中的随服务发布
采集器，再恢复剩余的显式安装。目录存在不是安装授权，不扫描目录自动导入。
恢复发生在出网 transport 接线与调度器启动之前。

每条记录先读取磁盘 manifest，比较其 checksum 与导入时保存的 checksum。
匹配后才允许在隔离子进程中导入代码并校验声明；清单变更（包括凭据前缀）必须
重新显式 import。checksum 只覆盖 manifest，不是代码签名，不能证明代码未变。
磁盘目录仍属于运行者的信任边界。

恢复不修改已保存的 enabled/disabled 决定。disabled 阻止采集，但不阻止启动时
的子进程导入校验；因此模块顶层代码可能在没有 active 源时执行。这明确取代
ADR 0023 对「无源插件永不执行」的描述，实际采集仍由源触发。

缺文件、坏代码、清单变化不会阻止整个服务启动。该插件不进入运行时注册表，
数据库审批记录保持原样，日志只输出插件 id 和修复提示，不输出异常正文。
修复缺失/损坏文件后可以重启重试；清单变化需显式重新 import。

## 理由与后果

- 比目录自动扫描更保守：卸载后保留的目录不会重新获得执行授权。
- 不新增 schema 或 API 字段。现有 `/v1/plugins` 只列运行时注册项；恢复失败的
  记录不出现在列表中，需结合启动警告排查，不将它误报为可用。
- 已安装来源暂由「持久化记录减去发布清单」识别，后续若发布包接管同名插件，
  必须明确迁移策略，不能仅改 trust。
- 启动执行逐个子进程验证，会增加启动延迟。注册表仍是模块状态；多 app 实例、
  生命周期集中管理和恢复失败的专用状态面不属于本次修复。
- 源目前没有持久化 collector 绑定；插件恢复失败后仍可能由别的匹配器接管。
  本次测试的非 RSS 页面会报 parse 失败，不承诺所有页面都能识别为插件不可用。

## 验证与可逆性

`tests/e2e/test_plugin_restart.py` 用两个独立 Uvicorn OS 进程、同一迁移后 SQLite
数据库、真实 HTTP origin 和插件子进程验证恢复、禁用、卸载、未审批目录、坏代码、
丢失清单以及凭据清单变化。删除 checksum 检查的隔离注入会让未重新审批的插件
成功写入条目，使测试失败；恢复检查后通过。

无需数据迁移即可撤回启动恢复逻辑，但撤回会重新引入重启后丢失执行注册的问题。
