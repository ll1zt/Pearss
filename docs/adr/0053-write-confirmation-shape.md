# ADR 0053：写确认的形状——一次确认 + 可选单字段编辑（两段式）

- 状态：superseded（[ADR 0058](0058-write-tools-do-not-elicit.md) 退役了整套写确认：写工具不再 elicit，`Confirmation`、四段 resolver、可编辑集与 `declined`/`aborted` 一并删除。本 ADR 保留为历史记录：#250/#251/#252 的形状决策以及它们当时解决的漂移问题）
- 日期：2026-10-03
- issue：#253（记录 #250 / #251 / #252 的决策；本 ADR 是 #253 的交付物）
- 相关 / 修订：ADR 0010（工具经 `/v1`，确认在 server 侧）、ADR 0036（工具面是 `/v1` 的语义投影）；**取代** `docs/api/mcp-tool-guide.md` 第三节里「每个写工具 elicited 一次，确认参数 == 执行参数」的呈现规则。**本身已被 ADR 0058 整体取代**（写工具不再 elicit）

**场景**：AC-238..245（已登记在 `SCENARIOS.md`，归属 #250 / #251 / #252；本 ADR 记录它们的共同决策，不新声明号段）。

## 背景

写操作必须经 elicitation 由用户确认（AGENTS.md；ADR 0010 定下确认在 server 侧）。早期实现把**派生字段逐个镜像进对话框**：用户确认的是一张表单，确认参数与执行参数**逐字段**比对。这套形状有两个代价：

- 每次写都让用户读回整个请求——一个 `add_sources` 的对话框列出全部字段，而用户实际上只是找一个「确认」的位置；
- 逐字段比对是**手写**的，12 个工具 12 份。#67 已经漏过一次字段，说明「两条清单靠人保持同步」本身就是缺陷源。

#250 把默认路径收敛为一次确认；#251 让每个工具显式声明「用户可改哪些字段」；#252 在这两者上加了「改一个字段」的路径。三次改动都改了工具面的**契约**（对话框形状、确认判据），但决策只散在 commit message 与 PR 正文里。本 ADR 把形状与理由记成一份。

## 决策

1. **默认路径 = 1 轮**。对话框的 schema 只有一项 `confirmed`（默认勾选 = 接受）；执行的字段由各工具 `_<tool>_fields()` **单一来源**派生，写进摘要（`message`）。对话框里没有可替换的字段，客户端回传的多余/异值字段**一律不读**（AC-240）。
2. **修改路径 = 两段式（+ 最终确认）**：

   - 轮 1：摘要 + `[x] confirmed` + 「改哪个字段？」受控单选 `edit`（enum = `none` ∪ 该工具可编辑集）；
   - 轮 2（仅当选了字段）：只问该字段的新值，按值类型渲染（布尔 = 勾选、数字 = 数字、**结构化值 = canonical JSON 文本**）；
   - 轮 3（仅当编辑）：展示**组合后的请求**并把该值回显给客户端；
   - 服务端用 `_matches` 校验「回显 == 将要执行」，不符即 `aborted` 且零写入（AC-244）。

   执行的字段 = 派生默认**覆盖**被编辑字段，其余逐项等于默认（AC-243）；任意一轮取消/拒绝 → `declined` 且零写入、零 Core API 审计行（AC-245）。
3. **每个写工具显式声明可编辑集**（确认构造器的必填参数，漏声明会在守卫处失败）：可编辑集 ⊆ 执行参数集；身份/目标类参数（`url`/`urls`/`type`/`items`/`item_ids`/`item_id`/`source_id`/`plugin_id`/`enrichment_id` 与 `*_fingerprint`）**不可编辑**——想改身份/目标的调用方重新发起请求（AC-241）。
4. **四段 resolver，不是三段**。框架把答案注入**消费者**，resolver 看不到自己的答案，所以「选 → 值 → 确认 → 组合」每轮一段、用 `Resolve(...)` 把答案传下去；依赖参数注解为 `ElicitationResult[...]`，这样任一轮取消/拒绝到达工具层是 `declined` 而不是框架的 `ToolError`。
5. **拒绝只有一种拼写**：`aborted` 由 `_aborted()` 唯一产出；`declined` 由 `_confirmation_verdict` 唯一产出（AC-76）。

## 安全性论证

确认要挡住的是「客户端确认 A、server 执行 B」。三层各自覆盖一段：

- **协议层**：SDK 用 `RequestStateSecurity.ephemeral()` 把 `request_state` 用 AES-GCM 封起来，里面是**整个 arguments 的摘要**；一个参数漂移的重试在工具体运行前就被拒为 `-32602 invalid_request_state`（实测，见 `tests/integration/test_submit_items_confirmation.py`）。
- **工具层（本模块的守卫）**：默认路径的执行值只来自**服务端派生**，对话框没有可替换的字段，所以客户端没有落脚点；编辑路径唯一的用户输入经轮 3 的 `_matches` 与「将执行的值」比对。
- **归属**：编辑值只在 `_guarded_write` 一处应用到请求体，且检查「该字段确实是这个请求体的字段」——落不到实处的 override 就是「改了等于没改」的静默失败。

结论：默认路径**没有漂移面**；编辑路径的漂移面收敛到**一个**值，且这个值在展示与执行之间可比对。

## AC-75 判据的迁移（理由与代价）

AC-75 原来是「确认覆盖全部执行参数」——它依赖对话框镜像字段。默认路径单轮化后，对话框不再镜像字段，判据迁移为：

> 任一入参变化都会改变**摘要**（`message`）。

代价与补偿：

- 代价：用户不再在对话框里逐字段核对执行值；「看得见」的粒度从「每个字段一行」变成「摘要一句话 + 可编辑面」。
- 补偿：摘要必须点名所有会执行的字段，所以迁移时做了一次全工具扫描，发现并修好 **3 个摘要漏参**（`add_sources` 的 chain/lang/trust/parser、`retry_enrichments` 的 source_id、`submit_items` 的 fingerprint）——这正是旧判据「逐字段比对」掩盖的地方。
- 形状断言被取代：AC-238 从「对话框属性集 == 全部派生字段」变为 `{confirmed, edit}`。

## 被否决

| 备选 | 否决理由 |
|---|---|
| 一次改**多个**字段 | 轮数随字段数增长，且每次确认必须覆盖**组合后**的请求；复杂度不划算，收益（一次改两处）少见 |
| 可编辑字段名用**自由文本** | 拼错会静默「改了等于没改」；受控 enum 让不存在的字段名**无可拼之处** |
| 改协议（自定义确认形状 / 非 MCP elicitation） | 承担协议适配成本，收益与 MCP 内建 elicitation 重叠（ADR 0010 已把确认放在 server 侧） |
| 逐字段展开（3 轮逐个问） | 默认路径就要多轮，用户代价高；单轮默认 + 按需编辑才把代价放在「真的想改」的时候 |
| 保留旧的逐字段表单（不改） | 每次写让用户读回整个请求；逐字段比对是 12 份手写清单，#67 已漏过一次 |

## 后果

- 默认写操作从「读回整个请求」变成「读一句摘要 + 勾选」；想改一个字段才付 3 轮。
- `editable` 成为工具面契约的一部分（守卫机械对账），第 13 个写工具自动纳入扫描。
- 约束：摘要必须点名所有执行值（AC-75 的新判据）；新增可编辑字段必须同时进入 `_editable` 与执行参数集。

## 可逆性

可逆：把默认路径改回逐字段表单是 `confirmation.py` 内的改动，工具主体不变。但**判据与守卫要一起改**（AC-75 / AC-238 / AC-241），且这是工具面契约、客户端会看到对话框形状变化——所以记录在此，而不是留给 commit message。
