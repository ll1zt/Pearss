# 0046 · 作业是一等公民：命令 / 账本 / 投影（六个复数形态坍缩为一个机制）

- 状态：accepted
- 日期：2026-10-01
- issue：#186（本 ADR 是 #186 的交付物；实现见 #187..#203，场景 AC-180..220）
- 取代 / 修订：**部分取代 [ADR 0045](0045-content-level-discovery.md) 的 D7（同步批量端点）与 D10（不新增持久化）**；修订 [ADR 0022](0022-agent-ingest-api.md) 的溯源边界挂点（D-A 采纳后挂 origin）、[ADR 0044](0044-batch-source-addition.md) 的「确认对象」（报告 → 作业）；与 [ADR 0036](0036-tool-face-is-a-semantic-projection.md)（工具面是投影）、[ADR 0037](0037-cancellation-semantics.md)（取消是执行语义）、[ADR 0034](0034-alert-when-intervention-is-needed.md)（循环存活）同向

**本 ADR 不占 AC**（决策记录，先例 #172）：每条场景由对应实现 issue 承担。

## 背景

**用户实测（2026-09-30，本 ADR 的直接起因）**：一次 568 个地址的全量回填投递，
`POST /v1/sources/{id}:fetch-items` 把 568 次抓取放进**一个 HTTP 请求**。网关超时了，
服务端跑完了（日志里 `stored 1 draft(s)` 一路刷到约 200 条），而**逐条结果随响应一起
不可达**——调用方付了全部成本，拿到一个超时，且无从查询哪些成功了。同一次会话量到：
40 个地址的工具结果约 10KB 进模型上下文，200 个地址必然触发网关超时。

现状（读代码，非推断）：

- **六个复数工具类型相同、实现各写一遍**：`add_sources`、`fetch_source_items`、
  `delete_items`、`delete_source_items`、`backfill_source`、`retry_enrichments` 的
  形状都是 `targets[] -> result[]`，于是六个都继承「报告随规模膨胀」，且各有各的确认。
- **投递单元不可寻址**：`raw_fetch` 表**没有 target 列**，`pipeline.fetch_items`
  也**根本不写 `raw_fetch`** → 「这个地址为什么没进来」在任何地方都问不出来。
- **已读/星标只有方言**：`/v1` 没有一等原子，只有 `src/app/reader/` 的 Google Reader
  兼容层；任何非 Reader 客户端想标已读都无路可走。
- **`source` 把事实与策略焊死**：一次 `DELETE /v1/sources/{id}` 同时销毁订阅与内容
  （不可逆），无法表达「我不想再订了，但我想留着已抓到的」。
- ADR 0045 选择了**同步批量**形态，因此整体继承了上面每一条。

四个根因（这四条是上面前三条的抽象，不是并列的第四组现象）：

1. **报告与操作融合**：响应体既是「这次调用做了什么」又是「结果是什么」，于是它同时
   受制于两件事——操作要多久、结果有多少。超时丢的是结果，不是操作。
2. **工作不是一等对象**：没有「一批工作」这个东西，所以它没有状态、没有句柄、没有地方
   记「每个目标怎么了」。
3. **单元是「这次调用」而不是「这个目标」**：地址不是被寻址的对象，而只是数组里的一项。
4. **策略与事实同表**：改订阅策略会碰到内容事实，反之亦然。

## 决策

### 1. 三条主设计律（+ 三条辅律）

**主律**

1. **效果 ≠ 报告。** 一个操作要么是 O(1) 的（做一件事、回答一个句柄），要么是查询。
   绝不出现「响应体是这次操作的结果清单」——那种响应的形状由输入规模决定，也就会在
   规模上失败。
2. **时间显式。** 时长不可控的工作必须返回 `202` + 句柄，而不是占着一个请求等它跑完。
   请求的生死与工作的生死从此无关。
3. **量不泄漏。** 输入是列表时，输出是句柄。响应的**字节数不随输入规模变化**——这是
   可断言的形式（见 §后果：10 个地址与 40 个地址的响应等长）。

**辅律**

4. **效果可寻址。** 每个持久效果都有一个可查询的地址：条目有 id，投递单元有
   `(work, target)`，作业有 `work_id`。「发生了什么」永远能事后查。
5. **失败是数据。** 失败不是异常，是账本里的一个 `outcome` + `error_class`。
   一条失败不影响其余（除非 origin 明确要求停）。
6. **幂等键由命令值派生。** 同一命令值（kind + 有序 targets + params）在飞时复用同一个
   作业；键不是调用方随手给的随机串，而是命令本身的哈希。

### 2. Work 与 Unit：唯一的复数形状

引入两个持久对象，六个复数形态从此只有一个机制：

```text
Work   (id, tenant_id, kind, status, targets_json, params_json,
        fingerprint, retry_of, correlation_id, created_at, finished_at)
Unit   (work_id, target, outcome, error_class, detail, ref, at)   PK = (work_id, target)
```

- `kind` ∈ {`fetch`, `delete`, `enrich`, `retry`, `ingest`, `subscribe`}：**意图**，
  不是端点名。
- `target` 是**被寻址的对象**（一个地址、一个条目 id、一个源 id），不是「数组第几项」。
- `Unit` 是**不可变**账本行：写一次，永不改写。`(work_id, target)` 是主键，
  所以「同一目标在同一作业里出现两次」在 DB 层就不可表达。
- `outcome` ∈ {`ok`, `skipped`, `rejected`, `failed`}，`error_class` 用既有五值
  taxonomy（`network`/`parse`/`structure_changed`/`blocked`/`auth`）。**`rejected`（没尝试）
  与 `failed`（尝试了但失败）严格分开**：只有后者值得重发。

### 3. 进度与统计是纯折叠，不是第二个事实源

```text
counts(work) = fold(units of work)   # {ok, skipped, rejected, failed} + queued + total
```

`counts` 每次读时从账本折叠出来，**不落库**（与 ADR 0009 对 `next_run_time` 的裁决同向：
两个事实源必然分叉）。`queued` 是派生的——没有账本行的 target 就是还没跑到的 target。
作业的终态（`succeeded`/`partial`/`failed`）也由折叠决定，不由执行器另写一个状态。

于是：句柄可以 O(1) 地带上统计（`GET /v1/works/{id}`），而**逐条结果只能从账本分页查询**
（`GET /v1/works/{id}/units`）。这正是「超时丢结果」结构性消失的地方——结果不在响应里，
它在库里，随时可再查。

### 4. 一个机制，六个投影

六个复数工具**坍缩为一个机制**（提交命令 → 执行器 → 账本），但 MCP 侧**保留意图命名**：
`fetch_source_items`、`delete_items`、`retry_enrichments` … 仍然是它们自己的工具，只是
改为「提交对应 kind 的作业」并返回句柄。**不做** `request_work(kind=…)` 这种万能工具：
工具名是模型选择的主要依据，把六个意图压成一个枚举会把这个依据拿掉。

读侧对称地收敛为两个工具：`get_work`（状态 + counts，常数大小）与 `work_units`
（逐条账本，分页 + `outcome` 过滤）。返回句柄的工具必须同时提供读到它的路径，否则
「不再内联结果」就是**能力被删**而不是**响应形状改变**。

### 5. 分层：原子与作业在 `/v1`，MCP 是 O(1) 投影，CLI 是批量入口

| 层 | 承担 |
| --- | --- |
| `/v1` | 原子（单目标）+ 作业（复数）：`POST /v1/works`、`GET /v1/works/{id}`、`/units`；单目标原子如 `POST /v1/sources/{id}:fetch-item`、`POST /v1/enrichments/{id}:retry`、`GET|PATCH /v1/items/{id}/read-state` |
| MCP | 意图命名的 O(1) 投影：返回句柄 + 统计，不返回逐条；读侧 `get_work`/`work_units` |
| CLI | 作业与批量入口：`just work …`（文件 → 命令值），供人而不只是模型使用 |

MCP 工具**一律经 `/v1`**（ADR 0010 未被修订的部分），因此审计、鉴权、幂等、校验只有
一条路径。

### 6. 事实 / 策略分离，及其余四项决策

**D-A 完整拆分**：`origin`（事实：URL、类型、抓取历史）与 `subscription`（策略：调度、
folder、trust、chain、启用状态）分表。**D-B**：`item` 挂 `origin_id`，去重身份 =
`(tenant, origin_id, external_id)`——同义且比「源」更准。**D-C**：频道身份 = **订阅**
（未读在条目上、归类在订阅上），因此一个 origin 可以有两个订阅。**D-D 退订 ≠ 销毁**：
`unsubscribe` 只停策略，销毁是**显式**动作、要理由、进审计。**D-E 阅读状态一等化**：
`/v1` 有 `read-state` 原子，Reader 兼容层的写路径改调它（方言不外渗，ADR 0005 的约束不变）。
**D-F 账本保留 30 天**：`work_unit` 不是长期档案，长期只留聚合计数——账本无限增长就是
第二个数据库。

### 7. 既有形态的处置

- `POST /v1/sources/{id}:fetch-items` 降级为**受限兼容 shim**（保留旧调用方可用，
  不再是新代码的路径）。
- ADR 0045 的 D7（同步端点）与 D10（不新增持久化）被本 ADR 取代：账本不是「新持久化」，
  它是**既缺的 provenance**——现状「不写 `raw_fetch`」本身就是缺陷，而 ADR 0045 的
  「不做续跑游标」仍然成立（续跑由账本查重天然给出，不需要游标）。

## 不做的（附理由）

- **调用方自己循环单目标端点、自己持有列表。** 对 agent 客户端是灾难：568 个目标要跨
  568 轮上下文持有，且中途失败要自己拼状态。**作业属于服务端。**
- **`sync-if-small` 双形态响应。** 同一调用的响应形状随规模变化，违反量不泄漏，
  客户端必须分支——分支写错的那一侧就是丢结果的那一侧。
- **把地址实体化、为 target 建表。** target 是 unit 的字段；建表只会带来生命周期问题
  （地址什么时候该被删？），而账本已经给了可寻址性。
- **一个万能 `request_work(kind=…)` MCP 工具。** 见 §4。
- **「消除副作用 / 纯函数式接口」。** 不可能也不该：目标是**把副作用收成一个执行器 +
  一张账本**，而不是假装没有副作用。

## 后果

- **正面**：超时不再丢结果（结果在库里）；「每个目标怎么了」可查、可过滤、可重发；
  六个机制变成一个；同一命令值在飞时不会重复执行；幂等键来自命令值而非调用方纪律。
- **代价**：多两张表与一个后台执行器；工具面多两个读工具（本 ADR 的实现里，工具面
  从 15,689 → 16,667 字符，预算由 16,000 提到 17,000——**数字要在 diff 里论证**，
  由 #197/#199 在坍缩六个宏工具时复审）；旧 `:fetch-items` 与新路径并存一段时间。
- **残余风险**：账本是 append-only 的事实源，`retry` 是**新作业**（`retry_of` 指回去），
  所以「同一目标的历史」会有多行——这是刻意的（重发也是事实），代价是查询时要按
  `work_id` 收敛。保留窗口（D-F，30 天）到期后逐条不可查，只剩聚合计数。

## 修订 2026-10-02（issue #211）：兼容壳的删除触发条件

§7 把 `POST /v1/sources/{id}:fetch-items` 降级为受限兼容壳，但没有写**什么时候可以删掉它**。
按 ADR 0041 的先例，有意推迟的东西要留下**可观测**的触发条件，否则下一个人只能猜。以下任一成立即删壳
（删壳 = 删端点 + `MAX_COMPAT_FETCH_ITEMS` + 它的测试；MCP 侧早已只经 `/v1/works`，
不再有第二条调用路径）：

1. **真实调用方已经不用它。** 判据：`audit_log` 里该 endpoint 的调用在**一个完整保留窗口
   （30 天）内为零**。可观测性来自审计中间件记录的是**路由模板**而非具体路径
   （`src/app/middleware.py::_operation`），所以这一条是一次计数：
   `select count(*) from audit_log where operation like 'POST /v1/sources/%:fetch-items'`
   ——不是「等一段时间」，而是「查得到零」。
   该可观测性由 `tests/integration/test_fetch_items.py` 的用例钉住：调用一次壳，审计行必须能被
   这条谓词选中。
2. **壳开始长功能。** 有人往这条路径加行为（新参数、新响应字段、新权限），
   即「一个机制两个入口」的维护成本已经超过它省下的迁移成本——那时它的价值是负的。
3. **下一次破坏式 API 变更窗口。** 与其它 breaking change 一起发，避免为删一个 endpoint
   单独制造一次兼容性事件。

**不在触发条件里**：「发一次新版本」「过半年」这类与调用方行为无关的时间判据——它们会在
没有任何人停止调用的情况下删掉一条仍被使用的路径。

保留这个壳的理由同样记在这里：**旧调用方不必改**（#192 的 declined 项不是「永久两套语义」，
而是「一个带删除条件的过渡形态」）。

## 修订 2026-10-02（issue #212）：`running` 的可认领性加租约

§后果·残余风险 把「`running` 可认领」当作续跑路径记下：进程死在半路，下一轮接着跑，
账本按 `(work_id,target)` 查重所以不会重复目标。实现后发现它还有第二层含义——`running`
也包含**还活着、只是慢**的作业。单进程部署下两种含义不会撞车（只有一个执行者），
但一旦出现第二个执行者（多进程 worker、把 worker 拆成独立进程、第二个实例），
第二个会把同一个作业再跑一遍：重复出网请求与 provider 预算，且到写 unit 撞主键才暴露。

修订：`claim_next_work` 对 `running` 只认「账本安静超过窗口」的作业（窗口由
`PEARSS_WORK_LEASE_SECONDS` 给，默认 900 秒；`0` 关闭）。每写一条 unit 就是一次心跳，
所以这是关于**存活**的判断而不是猜测；没有 unit 的 `running` 按 `created_at` 计时。
代价：异常退出（未捕获异常、被杀）的 pass 与「死了」不可区分，因此也等满一个窗口才续跑。
若将来要缩短这个代价，需要给作业加**持久化的 owner 身份**（enrichment 的 owner-token
先例），那是一次带迁移的改动，本修订不做。
