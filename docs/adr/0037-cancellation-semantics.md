# 0037 · 取消是执行语义：所有者写意图、协作式检查点、`cancelled` 终态

- 状态：accepted
- 日期：2026-09-29
- 补充：#90（仓库级评审台账 C10）。本 ADR **只定义语义，不实现**。

## 背景：词汇齐了，产生它的语义没齐

读代码得到的现状，比台账写的更具体：

| 已有的 | 在哪里 |
|---|---|
| `JobRunStatus.CANCELLED` 这个值 | `core/enums.py` |
| 数据库 CHECK 约束允许它 | `adapters/db_models.py`（`jobrunstatus`） |
| 状态机把它算作终态 | `core/job_state.py` 的 `TERMINAL_STATUSES` |
| **一个协作式取消原语** | `app/processor_runtime.py`：`cancelled: threading.Event`，在操作之间与 deadline 一起检查 |

**没有任何执行路径会写它。** run 的终态目前只有三个生产者：`scheduler`（`FAILED`）与 `scheduling.finish_job_run`（`SUCCEEDED` / `FAILED` / `TIMED_OUT`）。所以一次 run 被 claim 之后（`running` + `lease_expires_at`），要么跑完，要么被 `reap_orphaned_runs` 当作**孤儿**判超时——而超时的语义是「**租约过期**」，不是「**有人要它停**」。

于是台账里被分开记下的两件事，系统里只有第一件有实现：「放弃锁获取尝试」= 不认领即不做（现有能力）；「停止正在执行的工作」= 有一个**声明了却无人产生**的终态，加一个只在处理器层生效的取消标志。

**本 ADR 就是那缺失的一层语义。**

## 决策

### 1. 所有权与意图分离：取消是写意图，不是杀进程

run 的所有者是**持有它的执行者**（`owner_token` + `lease_expires_at` 已经存在）。取消请求写一条**取消意图**，由所有者**在自己的检查点看到并自行退出**。

进程级 kill（SIGTERM / 线程中断）被否决：它**无法区分「有人取消了」与「进程崩了」**——两者留下的现场完全一样，而这两个事实需要不同的处置（一个是预期的，一个是事故）。它还会绕过终态写入与审计，并在 SQLite 上可能留下半个事务。

### 2. 只在协作式检查点生效

检查点定义在**每条 entry 之间**与**每次外部调用之前**——也就是 `processor_runtime` 已经在检查 `cancelled` 的那些位置。**不做**抢占式中断：它需要线程/进程级控制，且会在写库中途留下半个事务。

后果（必须写清，否则实现时会假装取消是立即的）：**取消不是立即的**。检查点之间已经在做的工作会完成，包括已经发出的 provider 调用。

### 3. `cancelled` 与 `failed` 必须分开——这正是那个 enum 值存在的理由

- `failed` = 试过、没成 → **计入**失败率与告警（ADR 0034 的成功率塌陷条件正是数它）
- `cancelled` = 有人让它停 → **不计入**失败率，不进告警

把它们合成一个值会让告警与健康面板开始说谎：一次人为取消会表现为一次故障，而真正的事故会被淹没在噪音里。

### 4. `cancelled` 是终态，且不可回退

重跑是**新的一次 run**（与重试同一语义），不是把这一行改回 `queued`。`core/job_state.py` 的「终态不可回退」早已如此要求，`CANCELLED` 已经在 `TERMINAL_STATUSES` 里。

### 5. 对已终态的 run，取消是幂等 no-op

与 `delete_*` 的「重试必须与首次不可区分」同一原则：第二次取消不报错，也不改变任何东西。

### 6. 两件事不得合并成一个 endpoint

「移除排队中的工作」（队列操作）与「停止正在执行的工作」（执行语义）在 API 上**保持两个动作**。合并会让「取消」在某些状态下**静默降级成丢弃**：对一条还没被认领的 run，它悄悄变成队列操作；对一条正在跑的，它需要一个完全不同的机制。调用方以为自己在做同一件事，实际取决于它没看到的时序。

## 理由：被否掉的备选

| 备选 | 否掉的理由 |
|---|---|
| 进程级 kill / 线程中断 | 留下与崩溃一样的现场；绕过终态与审计；可能留半个事务 |
| 复用 `failed` | 人为取消会进失败率与告警，健康面因此说谎 |
| 复用 `TIMED_OUT` | 超时是「租约过期」这一**时刻**，取消是「有人要它停」这一**意图**；后者允许在取消后仍等所有者收尾并写下自己看到了取消 |
| 现在就实现 | 先定义再暴露。没有语义的实现会把「取消」固化成某个 endpoint 的行为，之后再改就是破坏性变更 |

## 后果

- **不新增任何 endpoint**；本 ADR 是后续实现的前提，也是「为什么现在没有取消按钮」的答案。
- 实现时的验收判据先写在这里，免得到时重新讨论：
  - 取消后 run 落 `cancelled`，且**不计入**失败率与告警
  - 检查点之间的工作会跑完（不半途丢产物）
  - 对已终态的 run 取消是 no-op
  - 「队列里未认领的工作被移除」与「正在跑的 run 被取消」在 API 上仍是两个动作
- `reap_orphaned_runs`（进程死了 → `timed_out`）与取消（人让它停 → `cancelled`）**必须保持可区分**，这是两个不同的事故类型。

## 可逆性

**定义**可逆（改本 ADR 即可）；**实现**难逆——终态进数据库、进客户端语义，且告警口径一旦按它调过，改回来会让历史数据有两种解释。
