# ADR 0039：循环互看（liveness 走告警通道）及其残余风险

- 状态：accepted
- 日期：2026-09-29
- 相关：ADR 0034（需要介入时主动告警）、ADR 0019（健康面）、issue #61

## 背景

ADR 0034 决策 3 列了三个需要人介入的条件，PR #60 只实现了第一个（成功率塌陷），
issue #61 补另外两个。其中「后台循环不存活」有一个结构性困难，值得单独记下来：

**循环无法报告自己的死亡。** 会发现它停掉的代码，就是停掉的那段。所以
「让循环自己上报心跳、超时即告警」在本进程内是**不可实现**的——超时判定同样
需要那个已经停掉的执行体来跑。

issue #61 列了三个方向，并明确要求：**「两个循环同时死时告警通道的行为必须
写明，不能默认它不会发生」**。

## 决策

### 1. 两个循环互看，各自把自己「看对方」的结果送进同一条告警通道

`Scheduler` 看 `EnrichmentWorker`，`EnrichmentWorker` 看 `Scheduler`。每边在自己
的 tick 上读对方的 `liveness()`，得到 `(alive, name)`，构造只带 `dead_loops` 的
verdict，走**同一个** `send_alert` 与**同一套**边沿/节流语义（ADR 0034）。

两个方向共用 `app/liveness_watch.py` 的 `LoopWatch`：写两遍就是两条会各自漂移的
边沿逻辑，迟早会在「说什么」或「多久说一次」上不一致。

### 2. 谁看谁，取决于「谁死了更糟」

scheduler 死掉时采集**整体停摆**——正是 issue #4 的形态——所以这一向是必须的，
不能只做反向。worker 死掉只影响处理链，但它同样是静默的，所以两向都做。

### 3. 告警体按条件说话，不套用成功率那套文案

一个挂掉的循环不是「成功率问题」：它的恢复不是「runs are succeeding again」
（可能根本没有 run 可判——这往往正是它死亡没被发现的原因），它的下一步也不是
「查共享依赖（代理、凭据、网络）」。所以 verdict 带一个 `subject` 字段，文案与
行动建议都随它分叉。

### 4. 残余风险：两个循环同时死

**两个都死时，两个 watch 都不跑，告警通道保持静默。** 这不是「不会发生」，而是
被接受的残余风险，理由是还有被动面：

- `/healthz` 由 **HTTP 层**回答，不由这两个循环回答（ADR 0019）——它仍会报 503；
- 部署单元的重启策略（`Restart=on-failure`）会尝试把服务拉起来；
- runbook 里有一步手工/外部轮询 `/healthz`（见 `docs/operations/runbook.md`）。

**为什么接受**：要覆盖「两个循环 + 承载它们的事件循环一起死」，唯一可靠的办法是
进程外的观察者。而那已经把告警责任推回给「有人拉」——ADR 0034 决策里否决过的
方向。用进程内代码去覆盖进程整体死亡，是拿一个必然失败的机制换一个虚假的安心。

**触发条件（何时该推翻本决策）**：如果实际部署里出现「两个循环同时死而无人察觉」
超过一次，说明被动面没有被真的使用，此时应引入进程外观察者（systemd
`WatchdogSec=` 或部署侧监控），而不是继续在进程内加代码。

## 后果

- 两个循环各自多一个每 tick 的 liveness 读取与一次可能的出网调用（仅在边沿）；
- 告警文案多一个 `subject` 维度，新增条件时**必须**一并给出它的 subject 与行动
  建议，否则会发出指向错误方向的告警（这正是本 ADR 记录的一个真实缺陷形态）；
- 告警延迟由 tick/sweep 间隔决定，不是即时的。
