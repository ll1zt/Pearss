# 0033: 同 host 并发度——同轮已认领的行在得知被拒后让位

Status: accepted
Date: 2026-09-26
Context: issue #57。ADR 0029 定义了三道边界（最小间隔、单轮上限、冷却期），但没有定义
**「一轮 sweep 内对同一 host 的并发度」**。后果：冷却期可以被同轮已认领的行绕过。

## 问题（已复现，机制确定）

`app/enrichment_worker.py` 的限速是两阶段的：

1. **认领阶段**（单线程）调 `HostPacer.reserve(host)`：检查冷却期与单轮上限，通过即占位。
2. **执行阶段**（worker 线程）在真正抓取前调 `HostPacer.pace(host)`：等待最小间隔。

单轮上限把它**同时放行**的多行交给线程池，而「这个 host 正在拒绝我们」只有**第一个
fetch 返回之后**才由 `record_blocked()` 写进冷却期。若被拒的对端响应慢，第二个 fetch
会在冷却期写好**之前**就完成等待并发出请求。

零网络复现（本地假 origin，只改响应延迟这一个变量，`cap=2`、`cooldown=300s`）：

```text
delay 0s -> 到达「正在拒绝」host 的请求数: 1   （符合设计）
delay 3s -> 到达「正在拒绝」host 的请求数: 2   （冷却期失效）
```

即被限速的 host 在同一轮里被多打一次，次数取决于对端响应有多慢。这与 ADR 0029 的
意图（「429 是让我们慢下来，而不是去试它的下一条」）直接相反，且**对被测端不可见**：
现有测试之所以长期为绿，是因为假 origin 立即应答，第一个 fetch 恰好在第二个
`pace()` 那 1 秒等待结束前写好了冷却期——测试依赖时序巧合，机器繁忙时偶发失败。

## 决策

### 1. 同一 host 同时只允许一次抓取在途（in-flight gate）

`pace(host)` 的准入顺序固定为两步，顺序本身是决策：

1. **先等该 host 上一个 fetch 结束，再取槽位**。决定「这次该不该发」的唯一事实——
   上一个是否被拒——只有在它返回之后才知道。只等间隔、不等结果，正是本 issue。
2. **再等最小间隔**（持槽等待），每轮重查冷却期。

槽位在实际抓取**结束**后由调用方释放（`release()`，在 `finally` 里），因此第二次派发
必然看到第一次的结果：要么冷却期已置位（拒绝并让位），要么 host 健康（放行）。

### 2. 这是「串行化」，不是「每轮一条」

必须写明，因为它是不做选项 1（把单轮上限改成「每 host 每轮只探一次」）的理由：
串行化只要求**不并发**，不要求**减少**。健康的 host 仍然可以在一轮里派发到上限
（间隔由决策 3 保证），因此正常吞吐不变——`cap=2` 的既有测试仍然得到 `[2, 2, 1]`。

代价是明确的：同 host 的第 N 条要等前一条**结束**（不只是等间隔）。对抓取型处理器而言
这正是想要的语义（下一次请求的前提是上一次的结论），代价是与一个慢站点的往返时间
成正比——而它本来就被 `min_interval` 与等待预算限制着。

### 3. 让位不消耗 attempt，且由 `finally` 保证释放

- 被拒绝的已认领行沿用 ADR 0029 的既有语义：**退回 queued、不消耗 attempt**，下一轮
  再试（现状 `pace()` 返回 False 的路径）。
- 释放发生在 `finally`，覆盖成功、分类失败、未预期异常、超时、取消五条出口。**漏释放
  的后果比不修还糟**：host 会被永久标记为忙，一次瞬时错误就变成该 host 的长期停摆。
  这一点由注入验证（去掉 `release()` → 上限测试变红）与单元测试同时钉住。

### 4. 等待有界，超预算即让位

等待沿用 ADR 0029 的预算（`max(min_interval * 4, 5s)`）。预算耗尽 → 返回 False → 该行
退回队列，**不**阻塞线程池。持槽等待循环用有界 `wait(min(0.25, remaining))`，因此预算
耗尽时必然能退出，不会被一个永不释放的持有者卡死。

### 5. 冷却期仍然是「跳过一段时间」，不是「永久」

`record_blocked()` 维持 ADR 0029 的语义（冷却窗口后自动恢复）。本决策只保证冷却期
**不能被同轮并行绕过**，不改变它的时长与解除条件。

## 已否决

- **把单轮上限改成「每 host 每轮只派发 1 条」**（issue 里的选项 1）：能消除竞态，但把
  正常源的吞吐无条件降到 1/轮，与「不无谓降低吞吐」的验收判据冲突。串行化达到同样的
  安全性而不付这个代价。
- **在认领阶段就为同 host 建可取消栅栏、被拒后取消尚未开始的行**（选项 2 的另一种写法）：
  取消已认领行需要跨会话写回（每个 worker 线程有自己的 session），复杂度显著高于
  「在抓取前等一下」，而收益相同。
- **把测试延迟调大以避开窗口**：把产品缺陷编码进测试，明确否决。
- **在处理器子进程内计时**：sandbox 每行一个新子进程，进程内计数器无法约束任何东西
  （ADR 0029 已记录）。本决策同样只在宿主侧实施。
- **给 `translate` 也加同 host 串行**：`PACED_PROCESSORS` 是有意的白名单（ADR 0029
  决策 3）——provider 是 operator 自己选的，按条目 host 限速它等于用错误的理由节流。

## 影响

- `src/app/fetch_pacing.py`：`HostPacer` 新增 `_in_flight` 表与 `release()`；`pace()`
  拆成 `_acquire`（等兄弟结束并取槽）+ `_await_interval`（持槽等间隔）。
- `src/app/enrichment_worker.py`：抓取包在 `try/finally` 里释放槽位；三条**未执行抓取**
  的提前返回路径（上游未就绪、认领后失去 owner、准入被拒）各自显式释放，否则会让
  下一条行等一个永远不会到来的回合。
- 无 migration、无 API/MCP 面变化、无新环境变量：本决策不新增旋钮，只补一条不变量的
  实施方式。
- `tests/integration/test_fetch_politeness.py`：假 origin 新增 `delay` 参数，冷却期测试
  改为**显式控制延迟**（不再依赖「runner 恰好够快」），并保留原测试。
- `tests/unit/test_fetch_pacing.py`（新）：纯逻辑真值表，含并发行为（一个线程持槽、
  另一个线程在栅栏处等待）。

## 验收

- Given 慢速应答 429 的 host（延迟 2s）、`cap=2`，When 一轮 sweep，Then 到达该 host 的
  请求数 == 1；When 下一轮，Then == 1（冷却期跨轮保持）。
- Given 正常（200）host、`cap=2`、5 条积压，When 三轮 sweep，Then 每轮仍为 `[2, 2, 1]`
  ——吞吐不因串行化下降。
- Given 槽位被持有，When 兄弟行尝试派发，Then 它等待而不是并发发出（单元测试用线程
  栅栏验证）。
- 注入式验证（均在提交后的树上）：
