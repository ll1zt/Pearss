# 0031: 翻译产物的结构——原标签壳回填，非文本节点不经 provider

Status: accepted（**部分 superseded**：[ADR 0054](0054-a-dropped-image-marker-keeps-the-image.md) 细化了 §47「丢弃标记而不猜」——丢掉的 `img` 标记改为保留图片；成对标记与排版类 void（`br`/`wbr`/`hr`）仍照本文）
Date: 2026-09-26
Context: issue #33。translate 的产物把条目 HTML 拍平成纯文本再逐行包 `<p>`，读者拿到的
「译文」是一大块无标题、无图、无链接的纯文字，而原文（ADR 0018 的 merge 叠在下面）却有
这些结构。零网络复现（本机伪造 provider 响应，喂含 h2/strong/figure+img/pre+code/ul/li/a
的正文）：11 个标签全部丢失，产物是单个 `<p>`，且多段正文被折成一段。

复现同时暴露 issue 未提到的**第二个缺陷**：`<pre><code>` 里的代码**被送进了 provider**
（provider 请求里出现 `bpftrace -e 'kprobe:do_sys_open'`），缩进与换行在往返中被折叠——
把代码交给为了通顺而改写文本的模型，是一次无意义的调用加一次真实的损坏机会。

## 决策

### 1. 走路线 A：块级切分 + 原标签壳回填（否决路线 B）

issue 列了两条路：

- **A**：按块级元素切分，逐块送翻译，回填到**原标签壳**；非文本节点原样保留。产物与原文同构。
- **B**：译文单独成文，在 Reader 输出上分层让用户切回原文。

选 **A**。B 不解决 issue 的根因——「译文本身难读」；用户在 Reader 里看到的那一层仍然是没有
标题和链接的一团文字。B 只是把「难读」标注得更清楚。

### 2. 翻译单元 = 块级元素，不是整篇、也不是行

切分点取**块级元素**（`h1-h6/p/li/blockquote/figcaption/dd/dt/td/th/summary/caption`）：
一个块 = 一个翻译单元，块的**文本整体**送 provider，回填进该块自己的标签壳。

不用「整篇送、按行回填」——那正是原实现，它假设 provider 返回的行与输入的行一一对应，
多段正文因此被折成一段（复现实测）。不用「按行送」——单行没有上下文，译文质量下降且不可
控。

**容器结构由原地改树保证**：解析后的文档树保留，只替换可翻译块的**内容**，最后整体序列化。
所以 `ul`/`figure`/`table`/`blockquote` 是「因为还在树上」而存活，不依赖切分逻辑记得补回包
装标签——第一版实现用扁平 unit 列表，`<ul>` 就这样丢了。

### 3. 块内 inline 元素用成对标记保留

块内的 `a/strong/em/code(行内)/...` 不送 provider，而是替换为**成对标记**
`[[0]]inner[[/0]]`，块的文本（含标记）整体送翻译，回填时把标记还原为原标签。

- **成对**而非单边：译文里的 inner 文本要能找回来放进原标签，单边标记会让标签里没有东西。
- 因此链接与强调在译文里仍然可用（issue 要的「同构」），而句子是**整体**送的——
  片段化翻译会产出语法不通的译文。
- provider 丢弃/重复/不配对标记时，**丢弃该标记**而不猜：正文活下来，代价是少一个标签。
  这是本机制唯一可能的损坏方式，且它损坏不了文本。
- 标记用 `[[n]]` 形式（文本里几乎不可能自然出现）。早期设计用过裸 `<T0>`，因为与真实
  内容里的尖括号无法区分而否决。

### 4. 非文本节点原样复制，绝不经 provider

`pre`/`code`（整块）、`img`、`svg`、`math` 原样序列化进产物：

- 代码不是散文，且**空白是语义**（缩进），一次散文往返还把它改成 400 字以内的自然语言。
- 图片无从翻译，`alt` 也不是送给 provider 的散文。

### 5. 每块一次请求；块间按位置对应，绝不串位

`MAX_CHARS` 仍生效：一个块的文本超过上限时按 `_segment` 切段，该块的译文是这些段的拼接。
其余情况**一块一请求**。

一次一块是刻意的取舍：一个块的整体必须完整到达 provider，否则回填进标签的会是半个句子；
且「哪一块失败了」变成可回答的问题。代价是请求数变成「每块一个」（实测一篇 4 段文章 4 次），
而不是一次。这与 ADR 0028 对 fulltext 的判断同向：宁可多一次往返，不要一个看起来合理、
内容错位的产物。

**串位是本设计最危险的失效模式**：若把「第 i 个回复」按全局位置分配给块，provider 少答一块
就会让其后每块都收到别人的译文——产物读起来完全正常，标题下却是错位的正文。因此：

- `_rebuild` 按块**独立消费**自己的回复，回复不足时该块**保留原文**（不借用邻居）；
- provider 返回空 content 仍走既有 `parse` 失败（`_parse_reply` 的契约不变），整项失败而非
  半错位发布。AC-22 钉住这条交互，并用注入确认（放行空回复 → 测试变红）。

### 6. 产物过消毒边界（本决策是安全回归的修复，必须写明）

改动前 translate **不需要**消毒：产物是把 provider 文本 `escape` 进新造的 `<p>` 标签，
文本永远只是文本。改为「把 provider 文本组装成标记」之后，这条安全性消失了——回复
`</p><script>steal(...)</script>` 会提前闭合块并把脚本写进产物，而每个 reader 都会提供它
（注入验证：去掉边界后，字符串原样落库）。

因此产物在 store 之前过 `sanitize_html`（ADR 0007 的同一 allowlist），与管线处理 feed
正文、fulltext 处理抽取结果同一条规则：**边界放在不可信输入变成存储内容的那一点**。
用 `<div>` 包裹是为了让片段按文档解析，随后**显式移除**该包装——它是解析装置不是内容，
留着会给每个译文条目凭空加一层元素。

顺序是「先绝对化、后消毒」：allowlist 允许 `href`/`src`，也限制 scheme，所以绝对化后的
http/https URL 能通过；测试钉住这条顺序，否则消毒会悄悄撤销 AC-21 的保证。

### 7. 相对 URL 绝对化

产物像 fulltext 产物一样渲染在别处（阅读器/手机），`a href`/`img src` 以条目 URL 为基绝对化。
与 #39 同一理由、同一方法；解析失败则原样返回（少一个绝对化，不该丢产物）。

### 8. 纯文本正文的产物形态不变

绝大多数 feed 是普通段落。没有结构的正文切出来就是若干个 `p` 单元，产物仍是段落序列
（AC-23 钉住：`<p>` 数不变、不新增 wrapper）。这条是为了防止「为了修结构化正文而给所有
正文加一层壳」。

## 已否决

- **路线 B（译文单独成文 + Reader 分层）**：不解决根因，见决策 1。
- **整篇送、按行回填**：原实现；假设行数一一对应，实测把多段折成一段。
- **把 inline 标签也拍平**（只保块级）：链接消失，读者无法点击——#33 明确要求保留链接。
  代价是实现的复杂度：标记需要成对、需要还原、需要处理 provider 弄丢标记，但链接是读者
  真会用的东西，值得这个代价。
- **把整块 HTML 送给 provider 让它返回 HTML**：把结构决定权交给模型，同一篇文章不同模型
  会产出不同标签集（甚至 `onclick`），而 trust 边界要求产物过白名单消毒、结构可控。
- **按 kind 规则表决定哪些块可翻译**：与 ADR 0030 同样的理由——位置/结构语义比映射表更小、
  更明显。这里用的是「标签名白名单」，不是「第 n 块」。
- **为 inline 重建猜测强调**：provider 返回的是散文，凭空补 `<strong>` 是编造。译文里的强调
  只在原文**确有**该强调且标记被保留时出现。
- **失败时整项失败**（当某块回复缺失时）：代价过高——provider 答了大部分块，为了一个块丢掉
  整篇译文不如保留该块原文。仅在 provider 明确返回空 content 时失败（那是既有契约）。

## 影响

- `src/plugins/processors/translate/processor.py`：新增 `_split_blocks`/`_collect_units`/
  `_flatten_inline`/`_rebuild`/`_fill_unit`/`_replace_content`/`_restore_inline`/
  `_absolutise`/`_paragraphs`；`process` 改为切块→逐块翻译→原地回填→绝对化。
  单段纯文本的路径与旧实现一致（`<p>` 序列），标题回退路径同样。
- 无 migration，无 API/MCP 面变化：产物形态变化对上层透明（Reader 仍按 kind 叠层，ADR 0018）。
- **request 数量变化**：同一篇文章现在每块一次 provider 调用。这影响的是 provider 账单与限速
  （#35 的 per-host 限速管的是抓取，不是 provider），需在 runbook 中记录。
- 存量译文仍是旧形态（单 `<p>`）：走 `backfill`/`retry_enrichments` 重排队，与 ADR 0030 同。
