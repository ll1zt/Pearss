# 0012 · 登录型采集器：允许使用用户自供凭据

- 状态：accepted
- 日期：2026-09-05
- 修订：`docs/guides/collector-guide.md` 第 14 行（采集器不得绕过登录限制/反自动化）

## 背景

collector-guide 第 14 行原本无条件禁止绕过登录限制与反自动化要求：

> 采集器不得绕过 robots.txt、登录限制、CAPTCHA、付费墙、访问控制或站点明确的
> 反自动化要求。遇到此类情况归类为 `blocked` 或 `auth`，而非尝试规避。

这条规则对**匿名爬虫**完全正确：未经授权的访问不是采集，是入侵。

但 X（Twitter）是个规则覆盖不到的情形：用户要订阅的是**自己账号的关注时间线**。
数据是用户自己的，账号是用户自己的，凭据由用户本人提供。这里不存在"绕过别人的
访问控制"——访问控制是账号所有者自己同意解除的。原规则把这两种情况混为一谈，
于是把一个用户自决的合法用法一并禁掉了。

## 决定

把第 14 行拆成两条，**默认禁令不变**，只为"用户自己的账号"开一个窄口子：

1. **匿名采集**（默认）：仍无条件禁止绕过登录墙、CAPTCHA、付费墙、反自动化。
   遇到即归 `blocked` / `auth`，不得规避。
2. **登录型采集**（新增，需显式配置）：仅当满足下列**全部**条件才允许 ——

| 条件 | 为什么是条件 |
|---|---|
| 凭据由**用户本人**通过环境提供，且该账号属于该用户 | 单用户系统。多用户下这条不成立，口子就会变成入侵通道 |
| 采集范围**不超出该账号自身可见的数据** | 允许"读我自己的时间线"，不允许"用我的会话去抓别人的私有数据" |
| 源必须**显式声明**为登录型，不因 URL 匹配而自动启用 | 默认关闭。误启用会让一次普通加源悄悄带上登录态请求 |
| 凭据缺失/失效时归 `auth` 并**停止**，不尝试规避 | 保留原规则的核心行为：不硬闯 |
| 凭据永不进日志、AuditLog、fixture、错误详情 | AGENTS.md 的密钥规则在此更吃紧，因为值是可长期使用的会话 |

## 明确接受的风险

这条决定不是没有代价的，写下来而不是藏起来：

- **违反 X 的服务条款**。X 的 ToS 禁止未经授权的自动化访问，包括逆向私有接口。
  本项目单用户、自部署，风险由运行者个人承担；ADR 的作用是让这个承担是**知情的**。
- **账号风控**：可能限流、要求验证、乃至封号。
- **私有接口不稳定**：`HomeLatestTimeline` 的 queryId 与响应结构由 X 单方变更，
  无兼容性承诺。故 queryId 自动恢复与 `structure_changed` 分类是必需件而非优化。
- **CookieCloud 引入第三方信任**：凭据经由自部署的同步服务下发。

## 实现约束

- 凭据只从环境读取（`PEARSS_X_AUTH_TOKEN` / `PEARSS_X_CT0`，或 CookieCloud），
  **不存进数据库**，不作为 `source` 的字段，不进 `adapter_config` 之类的通用配置列
- HTTP 层必须把 `auth_token`/`ct0` 当作与 API key 同级的秘密：脱敏列表包含
  `cookie`、`authorization`、`x-csrf-token`
- 401/403 → `auth`；429 → `blocked`；风控空响应（`data: null`）不得当成"没有新内容"
  静默成功，必须显式报错
- 限流与重试**不在采集器内**：页间间隔、退避、预算属 `adapters/http.py` 与调度器
  （见 collector-guide 的职责边界表）

## 与"不演练的备份不算备份"的关系

本 ADR 扩大了密钥面。在此之前项目尚无备份方案（§7.5 未完成）。
**登录型源本身不可重放恢复**：数据库丢了可以重建条目，但 `auth_token` 丢了要用户
重新导出。因此本 ADR 生效期间，凭据的备份/恢复属于 runbook 的显式步骤，不能假设
"重放即恢复"覆盖它。

## 后果

- collector-guide 第 14 行改写为两条，默认禁令保留
- 新增 `twitter` 采集器，`source.type='web'`，需 `PEARSS_X_*` 环境变量
- 未配置凭据时该源以 `auth` 失败并退避，不影响其他源
- 若将来变成多用户系统，本 ADR 的第二条前提失效，须 supersede
