# 0038 · 单租户是范围决定：假设命名一处、启动时校验、不做端到端隔离

- 状态：accepted
- 日期：2026-09-29
- 补充：#89（仓库级评审台账 C09）

## 背景：schema 里有一列，不等于端到端隔离

`tenant_id` 出现在每张事实表上，而执行路径假设只有一个值。这个假设原来以
`TENANT = "default"` 的形式散在**八个模块**里——读起来像八次巧合，而不是一个被反复
重申的决定。评审台账的原话是「对已声明的单用户范围这是可接受的，但 schema 里有一列
不等于端到端隔离保证」。

## 决策

1. **范围**：Pearss 是单用户系统，**不做**端到端多租户隔离（把 tenant 贯穿请求、后台
   任务与持久化）。理由：那是一项大工程，而在第二个租户存在之前价值为零；而它的一半
   ——有列、没贯穿——正是现状。
2. **假设命名一处**：`core/tenancy.py` 的 `SINGLE_TENANT`。八份副本已替换，且
   `tests/unit/test_structure_guards.py` 守着「除它之外不得硬编码」。
3. **假设可证伪**：`app/tenancy_check.py` 在启动时查每个带该列的表，出现别的 tenant
   就 **warning**。不 raise：行确实存在，拒绝启动会把一次数据意外变成一次宕机；但
   **沉默**不可接受——而沉默正是八份副本所保证的。
4. **列预留在、隔离不做**：本 ADR 把「执行路径不隔离」从隐含变成写明，不改任何行为。

## 触发条件（这条决定什么时候变成 bug）

满足其一就重做这道题：**第二个用户**（不是第二个 feed）、**托管部署**、**家庭共享
实例**。任一出现，假设就变成 bug，而失败形态是「一个租户的行出现在另一个租户的读取
里」——所以触发条件是需求，不是日期。

## 后果

- 今天的行为一字未变（同一个值、同一批查询）。变的是它现在**只有一个家**，且**错了
  会响**：一个只在新表上出现的 tenant 会在 journal 里被点名，而不是无声消失。
- 新增一张带 `tenant_id` 的表时，启动校验的清单必须跟上，否则「新表里的租户」不会被
  报出来——也就是这道检查要消除的那种沉默。这不靠人记：`TENANT_TABLES` 的取值是从
  **已迁移的 schema 量出来的**，而 `tests/unit/test_structure_guards.py` 读 schema 与它
  对账，不一致就红。第一版清单凭想象写了 `audit_log`，而那张表根本没有这一列。
- 反方向（真要做多租户）也要从这里开始：先读本 ADR 的触发条件，再决定范围。

## 可逆性

**可逆**。实现端到端隔离是本 ADR 的反向操作，而它留下的两样东西（命名一处、启动校验）
在那种世界里**仍然是对的**——一个多租户系统同样需要知道数据里有几个租户。
